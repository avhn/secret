# Windows exec plan: long-lived stdio launchers

Windows `exec` currently terminates long-lived servers after 15 seconds and relays their output through supervised pipes. Make configured stdio MCP launchers indefinite, with directly inherited standard handles in production, while retaining atomic Job containment and checked cleanup. This is a behavior proposal, not implementation, release authorization or evidence of client compatibility.

## Scope and assumptions

- Target the staged Go CLI on Windows. Preserve Unix `syscall.Exec`, filtered `run`, template execution, importers, environment selection, storage gates and every agent-denial rule. No dependencies, flags, client configuration edits or installed-default changes.
- Production `main` supplies `*os.File` streams, but `cli.Main` accepts arbitrary output writers. Preserve those callers through an explicit relay fallback; never substitute global stdout/stderr for supplied streams.
- A configured launcher may consume values; it remains distinct from the names-only `mcp --store` server. `exec` is unfiltered and not an agent retrieval route. Third-party servers own their protocol, output and graceful shutdown.

## Current and proposed flow

```text
Before: host stdin -----------------------------> child
        child stdout/stderr -> pipes -> io.Copy -> supplied writers
        secret -> Job + wait + 15 s deadline + 250 ms drain

After:  host stdio -> duplicated restricted handles -> child
        secret -> same atomic Job + indefinite wait + checked Close
        non-file output writer -> existing relay, no runtime deadline
        run/importers -> existing bounded supervision, unchanged
```

## Binding behavior contract

- **Lifetime:** All Windows `exec` invocations lose the 15-second runtime deadline, including relay fallback. Store preparation retains its existing bounds. Direct exec waits for the direct child, not stream EOF or descendant lifetime. A server may remain idle indefinitely; no heartbeat, idle timeout or MCP parser is added.
- **Direct streams:** When both outputs are non-nil `*os.File`, pass `c.in`, `c.out` and `c.errOut` to `StartWindowsProcess`. Its existing duplicated-handle list supplies stdin/stdout/stderr without CLI-owned output pipes, copying, decoding or filtering. Preserve stream separation and bytes; emit no success banner or protocol text. Caller-owned files stay open and caller-owned.
- **Output-failure change:** Direct exec cannot observe child writes and no longer enforces output-error cancellation, the two-second stalled-writer bound or the 250 ms inherited-pipe drain. Broken pipes and backpressure belong to the server. A blocked or error-ignoring server can remain alive indefinitely. This explicitly supersedes the exec portions of M5a's recorded output-failure contract; it does not change `run`.
- **Non-file writers:** If either output is not `*os.File`, relay both through the existing `io.Copy` supervisor, honoring both supplied writers. Use `maxRun=0`, retaining two-second writer protection, output-error cancellation and 250 ms post-child pipe drain. Mixed file/buffer callers take this fallback. Today the 15-second deadline is the relay's only escape when native termination does not complete: `superviseChild` calls `kill` on grace expiry or output failure without starting a bounded wait, still requires the wait notification before draining, and `WindowsProcess.Kill` ignores the termination result. Add an exec-only shutdown bound (two seconds) that starts at cancellation escalation or output failure, independent of the unlimited normal lifetime, and reaches checked `Close` without another wait notification. `run` and Unix keep their current policies. Typed-nil files and invalid handles fail before child execution, with fixed diagnostics; never retry with global streams.
- **Containment:** Keep `PROC_THREAD_ATTRIBUTE_JOB_LIST`, restricted duplicated stdio handles, the non-inheritable `KILL_ON_JOB_CLOSE` Job and no breakaway. Unsupported enrollment or incompatible enclosing Jobs fail before execution, without suspended, assign-after-start or unenrolled retries. Direct inheritance is not permission to broaden the handle list.
- **Normal exit:** Always execute checked `WindowsProcess.Close`, including after successful direct-child exit. It terminates remaining descendants and confirms termination using retained process handles within its existing two-second cleanup budget. Direct exec does not fail merely because descendants inherited stdout/stderr. Descendant output completion is not promised after the direct child exits.
- **Signals:** Register the existing interrupt/termination notifications before creation and preserve the pre-start cancellation check. Forward observed cancellation using scoped `ForwardInterrupt`, never broadcast. The first signal starts a two-second grace period; repeated signals do not extend it. On expiry, terminate the Job and enter bounded checked cleanup without waiting indefinitely for a separate wait notification.
- **Console limitations:** Consoleless hosts have no CTRL_BREAK delivery guarantee. A synthetic signal-channel test is not evidence that a detached host can deliver console events. Forced wrapper termination cannot run Go defers, report cleanup status or promise application cleanup; closing its sole Job handle still triggers kernel termination.
- **Exit codes and failures:** After successful cleanup, return the direct child's full native uint32 status through the supported 64-bit CLI. An observed cancellation returns `128 + signal` instead; launch, wait or cleanup failure returns 1, taking precedence over child success or cancellation. Use fixed value-free diagnostics through bounded `runFailure`; preserve relay output/drain failure behavior. The same precedence applies to relay exec: today `launch_windows.go` collapses `WindowsProcess.Wait` errors into status 1 and `superviseChild` then lets an observed cancellation win, so relay exec could return 130 with no diagnostic. Keep the native wait error separate for exec relay and apply failure precedence after supervision. Forced wrapper exit status belongs to the terminating host, not this return contract.

## Host disappearance and shutdown ownership

Do not add a host-disappearance watcher. Reading or relaying stdin to detect EOF would compete with the server and change direct inheritance. Watching the immediate parent would require new identity/lifetime machinery and would confuse intermediary launcher exit with MCP-host death. Output probing cannot reliably establish host liveness.

Graceful shutdown is therefore server-owned: the host closes its stdin writer, the server handles EOF, exits, and secret cleans remaining Job members. Forced shutdown is host-owned: after its shutdown budget, the host must terminate the secret wrapper if the server ignores EOF. Host death does not necessarily kill secret. Only wrapper death closes its Job handle automatically; an enclosing host Job may additionally contain the wrapper, but that is host-specific evidence, not a guarantee. Document this deliberate tradeoff rather than implying universal parent-death protection.

## Security and compatibility boundaries

Keep value buffers cleared in `launch` before `execChild`, and keep the UTF-16 environment block cleared when native creation returns, before the indefinite wait. Environment string copies remain GC-managed and cannot be securely erased; do not claim otherwise. Preserve case-insensitive selection/removal, absent optional-key removal, encoding rejection and child PATH/PATHEXT lookup without an implicit shell. Values never enter launcher argv, diagnostics, JSON or audit; unfiltered server output can disclose them.

No store migration is needed. Existing buffered callers remain supported, but their output-failure behavior intentionally differs from production direct inheritance. Direct exec with pipe-holding descendants changes from drain failure to the direct-child status after confirmed containment. No `run` expectation changes.

## Verification and evidence gates

- **Native direct path:** Exchange synthetic protocol messages before and after at least 20 seconds, then close stdin and require orderly exit. Verify exact stdout bytes, separate stderr, required/optional selection and nonzero/full-width status through real files/pipes and the CLI subprocess.
- **Shutdown ownership:** Launch detached/no-console. Prove EOF-aware shutdown; separately prove an EOF-ignoring server remains alive until forced wrapper termination. Kill a synthetic host without killing the wrapper and record that distinction. Pin wrapper, child and descendant handles while alive; use native waits, never socket closure or post-exit PID lookup, as termination evidence.
- **Output and descendants:** Keep the direct child blocked on unread output beyond two seconds, then terminate the wrapper and verify containment. Exercise a child that survives an output error. Exit a direct child with live pipe-holding and closed-output descendants; require checked cleanup and the child's status. Retain relay drain failures and writer error/stall tests.
- **Regression:** Preserve `TestWindowsRunDeadline`, run output-failure/stall tests, UTF-8/UTF-16 redaction, console grace, template cleanup ordering, importer bounds, Unix execution and exact hook/CLI inventories. Test fallback exec beyond 15 seconds without weakening its output supervision.
- **CI:** Use Go 1.27.3 with `GOTOOLCHAIN=local`; run formatting, build, vet, uncached tests and internal race tests, focused Windows tests, setup checks and applicable existing shell/provider/inventory gates. Require green applicable jobs in `.github/workflows/ci.yml`, including both Windows lanes. Cross-vet and compilation are not native evidence. All fixtures use disposable roots; no real credentials, network MCP server or local provider activation.

In setup documentation, add a separate configured-launcher example using the installer's absolute executable path and argv equivalent to `exec -f STORE --key OPENPROJECT_API_TOKEN --optional-key X -- uvx openproject-ce-mcp@0.4.1`. STORE must be an explicit approved reference; configuration contains names, never values. Label this behavior unreleased until publication and distinguish it from names-only MCP setup. Claude Code, Codex and OpenCode compatibility requires versioned real-host startup, reconnect and shutdown evidence; synthetic tests establish none of those claims and no hook protection.
